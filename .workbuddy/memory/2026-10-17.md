## 详情页性能优化（用户：进入详情非常慢，本地优先、没有才抓、第一次抓完都存下来）

### 实测定位（不猜，先量化）

| 步骤 | 耗时 | 问题 |
|---|---|---|
| `_load_bars` 日线 | **514 ms/次** | 判断是 `cached[-1].date == today`，周末/节假日永不成立 → **每次进详情都联网重抓 400 根** |
| `_sectors_for` 反查板块 | **5669 ms** | 全库 `stock_sectors` 只有 2 行，新股票每次都要联网（1 次产业链 + 最多 3 次板块搜索 × 3s 间隔） |
| 板块 K 线 `_reference_bars` | 559 ms（首次） | 首次抓取，之后有 bars(fq='ref') 缓存 |
| 大盘 K 线 | 3 ms | 已缓存 |
| 本地查询（bars/signals/名字） | 全部 ms 级 | 无问题 |

→ 首次点开一只未缓存股票约 **6.8 秒**。

### 改动

**`backend/store.py`**：新增 `fetch_stamps(kind, key, fetched_at)` 表 + `fetch_stamp()` / `mark_fetch()` / `fetched_within()`。这是"抓一次就记住"的落地机制。

**`backend/service.py`**：
1. `_load_bars` 改三重短路：① 缓存新鲜（最后一根 >= **全库最新交易日**）→ 零联网；② 冷却戳内抓过 → 用缓存；③ 才联网，抓完落库 + 记戳。**失败也记戳**，避免每次白等超时。
   - 用「全库最新交易日」而不是 `today`：全市场扫描每天都在推进这个日期，它才是"已知数据边界"；停牌股永远追不上，由第 ② 条兜住。
2. 新增常量 `BARS_COOLDOWN_SECONDS=6h`、**`MINUTE_BARS_COOLDOWN_SECONDS=5min`**、`SECTOR_MISS_COOLDOWN_SECONDS=6h`。
3. `_sectors_for` / `_reference_bars` 加冷却戳：**抓空/失败也记戳**（板块反查抓空说明该代码无板块映射，重试同样白等 5.7 秒）。
4. **板块 + 同期对比移出 `analyze_symbol` 主链路**：只有已有板块缓存（纯本地无网络）才直接带上；否则返回 `comparison.lazy=True`。新增 `comparison_payload()` 供独立接口。
5. `symbol_success_rate(..., bars=)` 加可选参数，复用 analyze 已加载的 400 根，省一次查询。

**`backend/app.py`**：新增 `GET /api/analysis/comparison?symbol=&period=`。

**`frontend/index.html`**：`runAnalyze` 改为**先渲染 K线/结论/明细，再补对比**；新增 `loadComparison()`（带 `comparisonToken` 竞态守卫，快速左右切换时丢弃过期响应）；`renderComparison` 对 `lazy` 直接跳过（避免两个"加载中"打架），两者皆空时隐藏对比条。

### 效果（本地实测，落库缓存）

| 场景 | 改造前 | 改造后 |
|---|---|---|
| 详情首次（完全无缓存） | ~6800 ms | **610 ms** |
| 详情再次 | ~540 ms | **38 ms** |
| 详情（缓存全热） | — | 37 ms |
| 板块对比接口首次 | 阻塞首屏 5.7s | 6.1s **后台异步**（不挡首屏） |
| 板块对比接口第二次 | — | **4 ms** |

### 必须记住的两个坑

1. **分钟级别绝不能沿用日线的长冷却**。原实现"分钟每次必抓"是有意为之——分钟 K 盘中在变，用 6 小时冷却会让日内择时拿上午数据判下午。所以拆出 `MINUTE_BARS_COOLDOWN_SECONDS=5min`，并加测试锁住两个常量不许合并。
2. **类里引用模块级常量不能写 `self.XXX`**。我第一版在 `_load_bars` 里写了 `self.BARS_COOLDOWN_SECONDS`，运行即 `AttributeError`（py_compile 查不出来，只有真正跑用例才暴露）。

git 历史只有 2 个 commit，`git log -S "大图"` 无结果——不是回归，是功能一直缺失。用户期望「点击 K 线图放大查看」，本轮新增。

### 实现
- **`buildChartOption(data)`**：把 renderChart 里约 140 行 option 构建逻辑抽成独立函数，主图与大图共用
- **大图 modal**：`#chart-modal`（全屏遮罩 + 94vw×92vh 大图），点主图打开、Esc/点遮罩/按钮关闭，大图默认放大最近 40%
- **点击绑定用容器原生 DOM 事件**：`$('chart').addEventListener('click', ...)`。踩坑：`chart.on('click')` 只在点中图形元素时触发、`getZr().on('click')` 点空白也不可靠——原生 DOM 冒泡覆盖整块画布最稳

### 顺手修掉的真实 bug + 优化
1. **resize 监听器泄漏**：原 renderChart 每次 `window.addEventListener('resize', ...)`，多次分析堆积监听器（重复 resize + 内存泄漏）→ 移到 init 块只注册一次
2. **三级别并排重复请求**：原每次分析都 dispose 重建 3 个 echarts + 重新请求 m30/m15（触发数据源限流）→ 加 `tfCache`（同 symbol+period 只请求一次）+ `tfState.charts`（symbol 不变复用实例）；强制刷新时清空缓存
3. **tab 切换后图表 0 尺寸**：switchTab 切回 stock 时补 `state.chart.resize()`（ECharts 在 display:none 容器 init 会拿 0 尺寸）

### 验证
- 前端契约测试 +4 例（`ChartBigViewContractTest`），全量 408 例 + 契约 73 例全绿
- CDP 实测：真实鼠标点击 canvas 打开大图、大图渲染 canvas + 标题、Esc 关闭、多次分析无 JS 错误、三级别缓存 3 个 key

## 体系选股池（用户「如何根据交易体系选出高胜算股票池」→「开始编码」）

体系的价值闭环最后一环：把特征/增益/验证落到「今天该关注哪些票」。

### 实现
- **Store**：`recent_outcomes(cutoff, period)` 取最近 N 交易日买点样本（含已算特征）
- **service**：`system_pick(days=3, min_score=0, limit=100)` —— 取最近买点 → 用最新快照增益打分 → 按分降序 → min_score 过滤；复用 signal_outcomes 已算特征，**不 load K 线、不联网、毫秒级**
- **app**：`GET /api/system/pick`
- **前端**：独立「体系选股」页签，高胜算股票池表格（体系分/代码/名称/买点/信号日/信号价/命中特征 tooltip），搜索 + 按买点类型筛选，点击跳个股
- **测试**：`tests/test_system_pick.py`（4 例）+ 前端契约 `TradingSystemPickContractTest`（3 例）

### 真实数据结果（近 3 交易日 246 个买点，91 只分>0）
TOP：盟固利(+0.599 三买)、金龙羽(+0.462)、国新健康(+0.448)… **9/10 是三买**——因为体系学到「三买平均最大涨幅最高(10.63%)」，这符合预期。

### 关键设计决策
- **选股复用 signal_outcomes 特征**（不重新 load K 线），所以选股基于「最近一次 rebuild」，返回标注 cutoff。当天新扫描后要先 rebuild 再选股。
- **打分可解释**：每条带 hits 明细（+N/-N 摘要 + tooltip 全文），每一分追溯到具体特征箱。
- 检查顺序：先交易日历（空→「先扫描」）再快照（空→「先重建」），空库时给最贴切的提示。

### CDP 实测 7/7

## 修复：K线图「有时」空白（用户报告）

### 根因（真 bug）
`showChartLoading` 里 `chart.style.display = 'none'`，而 `runAnalyze` 的执行顺序是
showChartLoading → renderChart（echarts.init）→ hideChartLoading。
**首次分析时** chart 尚未 init，`echarts.init` 在 display:none 容器上拿到 0 尺寸，
之后 hideChartLoading 恢复 display 但**没有 resize** → 图表空白。
「有时」的由来：第二次分析时实例已 init、canvas 尺寸已缓存，setOption 不重新读
容器尺寸，所以正常——只有「首次进入个股页」或「切主题重建」时踩雷。

### 修复
loading 改成**绝对定位覆盖层**盖在 chart 上方，不再动 chart 的 display：
- HTML：`<div class="chart-box"><div id="chart"></div><div id="chart-loading"></div></div>`
- CSS：`.chart-box{position:relative}` + `.chart-loading{position:absolute;inset:0}`
- JS：showChartLoading/hideChartLoading 只切 loading 的 display，不再碰 chart
- 契约测试 `test_chart_loading_does_not_hide_chart` 锁死「showChartLoading 不得改 chart.style.display」

### 验证
- 全量 420 例 + 契约 78 例全绿
- CDP 实测：首次分析 canvas 1183×520、连续切换 5 只票尺寸稳定、loading 正常隐藏

### 顺带发现的独立问题（未修，待用户定夺）
连续快速切换/请求会触发**数据源限流**（后端退避重试 20s+40s），此时 analyze 卡住、
loading 一直转。这是数据源层问题，前端可加「请求超时提示」优化，但与图表渲染无关。

## 修复：体系选股有信号、详情 K线图没有（用户「体系选股显示 10-16 但详情没有对应买点」）

### 根因（数据一致性 bug，非图表渲染）
sz000001 的 `THIRD_BUY 2026-10-16` 的 `created_at = 2026-10-16 10:51`（**盘中上午**），
是盘中扫描用未收盘价写入的。收盘后数据更新：中枢 366..392 的 ZG=11.5，而 10-15 回调
low=11.26 **跌破中枢上沿** → 三买严格不成立，实时 scan 正确地不复现。
但 signals 表残留这个「过时信号」，体系选股读 signals 表快照、详情读实时 scan → 不一致。

### 修复：analyze 时清除「窗口内不复现」的过时信号（根治，不是把脏信号画进详情）
- **Store**：`delete_signals` + `delete_outcomes`（按 symbol+kind+date+period 删）
- **service**：`_prune_stale_signals(symbol, bars, signals)`——只清 `trade_date >= bars[0].date`
  （窗口内）且不在实时 scan 结果的旧信号，**窗口外历史信号保留**（窗口裁剪本身会丢信号，不能误删）；
  同时删 signal_outcomes 对应结局样本（体系选股立即干净，不等下次 rebuild）
- **analyze_symbol**：scan + save_signals 后调用 `_prune_stale_signals`

### 验证
- 真实数据：analyze sz000001 后，signals 表 + signal_outcomes 里 10-16 三买都清空
- `tests/test_signal_prune.py`（5 例）：删窗口内过时 / 保留窗口外 / 保留复现 / 同步删 outcomes / analyze 端到端
- 全量 426 例全绿

### 关键判断（别改回去）
- 「窗口内、实时 scan 不复现」的信号 = 过时信号（盘中脏数据 / config 变化 / qfq 漂移），删是「修正」不是「破坏」。
- 窗口外（trade_date < bars[0].date）绝不删——窗口裁剪会让老信号不复现，删了丢历史。
- 这是「渐进式清理」：analyze 一只清一只，全市场扫描会逐只清；盘中扫描仍会写脏信号，但下次 analyze/收盘重扫会清掉。

## 失效买点归入历史（用户「最新买点如果不存在应该放到收起历史列表中」）

### 用户场景
sz301047：三买 2026-01-19 显示「最新 +0.159」，但 2026-08-24 已出一卖——行情已走完几个月了还顶着「最新」徽章，误导成当前机会。

### 口径（**2026-10-17 第二轮迭代后敲定**）
**信号日距最新一根 K 线 > 3 个交易日 → 一律归历史**。在这条窗口之内 + 后端 `is_active` 未判 False 的才突出为「最新」。

演进：
- v1（初版）：每类买点取最新一条突出。→ 失效的也突出。
- v2（卖点口径）：出了卖点 → inactive 归历史。→ 但没出卖点、行情走老了的（如 9 个月前的）还是突出。
- **v3（当前，时间窗口口径）**：3 个交易日窗口一刀切。理由：「最新买点」的语义就该是「最近几天出现的买点」；9 个月前的信号不管出没出卖点，都已经不是「当前机会」。

### 实现要点
- 用 **`bars` 的日期序列算交易日距离**，不用自然日——周末/长假会让自然日虚高，把刚出的买点误归历史。
- 信号日不在 bars 窗口内（被裁剪掉）→ 视作 Infinity → 归历史（窗口外的信号本来就是远古信号）。
- `is_active !== false` 与交易日距离 `<= 3` 是**与关系**：避免「3 日内出了卖点又立刻出新买点」时旧失效买点混进最新组。
- 常量 `SM_LATEST_WINDOW_DAYS = 3` 在前端写死，与「三日买卖点池」页签的 3 日口径一致。

### 改动
- **后端 `_system_match_for_signals`**：加 `is_active` 字段，`is_active = not any(sd > sig.date for sd in sell_dates)`
- **前端 `renderSystemMatch(matches, bars)`**：第二参数接 K 线用于交易日距离计算；调用处改为 `renderSystemMatch(data.system_match, data.bars)`
- **空态提示**：`latest` 组为空且 `history` 非空时，加一行 `近 3 个交易日无新买点，以下为历史信号`，避免用户误以为体系没打分
- **契约测试**：`test_match_latest_and_history_split` 断言 `SM_LATEST_WINDOW_DAYS` / `tradingDaysFromLast` / 新调用形式；`test_stock_match_rendered` 同步

### 验证
- 真实数据 sz301047：2026-01-19 三买 dist=177、2025-11-10 三买 dist=225 → 均 HISTORY ✓
- 全量回归 **426 例全绿**（skipped=8）

### 关键判断（别改回去）
- 「最新」的语义权在用户手里。技术上 is_active（卖点口径）更精细，但用户看「最新」想的是「当前可操作的机会」——9 个月前的信号哪怕没出卖点，也早已不是机会。
- 3 日窗口与「三日买卖点池」页签对齐，前后口径一致，用户不用记两套规则。

## 四个视图买点数量对不上：根因排查 + 口径统一（用户「市场扫描/关注圈/三日池/体系选股同一买点数对不上」）

### 实测差异（服务器 stock.temeu.top，2026-10-17 22:57 刚扫完全市场）

| 视图 | 一买 | 二买 | 三买 | 窗口 | 数据源 |
|---|---|---|---|---|---|
| 市场扫描 | 145 | 4 | 242 | 30 **自然日** | scan_hits 快照 |
| 三日池 | 470 | 38 | 83 | 3 **交易日** | signals 表 |
| 关注圈 | 88（近3日） | 29 | — | 状态机全历史 | watchlist 表 |
| 体系选股 | 387 | 37 | 76 | 3 交易日+分数 | signal_outcomes |

同 20 交易日窗口对比更刺眼：**signals 一买 1404 条 vs scan_hits 145 条**，差近 10 倍。

### 三个真实缺陷

1. **`scan_hits` 主键 `(run_id, symbol, kind)` 缺 `trade_date`**
   一次扫描里同一股票 400 根 K 线产出多个同类买点，后者覆盖前者 → 每股票每类只留一条。
   这是数量差 10 倍的**直接原因**。
2. **`candidates` 读 scan_hits 快照，`pools` 读 signals 表**
   两者是不同数据源：analyze 个股会把新信号写进 signals，但永不写 scan_hits；
   `_prune_stale_signals` 清 signals 也不同步 scan_hits。→ 同一买点在不同页签出现/消失。
3. **关注圈僵尸记录**：二买确认后，超过 `max_wait_bars` 时原代码直接 `return items`，
   状态永久停在 OPPORTUNITY。实测服务器 49 条 >365 天的僵尸（最老 591 天），
   占着 active 位导致新一买无法开新一轮（sz002370 一买一直是 2025-03-12）。

另有一个**功能缺失**：`_attach_pool_rates` 只在 `risk_pool`（卖点池）里调用，
**买点池的胜算列一直是空的「—」**——这才是用户要求「把体系分放到胜算列」时看到的空白。

### 修复

- **`candidates` 改读 signals 表**，窗口改交易日语义，复用 `_group_recent` 去重，
  返回 `trading_dates` / `source` / `dedup` 供前端展示口径。→ `candidates(N)` 与 `pools(N)` 完全相等。
- **`scan_hits` 主键加 `trade_date`** + 幂等迁移 `_migrate_scan_hits_identity`
  （`PRAGMA index_list` 判定，重建表 + 保留全量行）。
- **`pools()` 补 `_attach_pool_rates`**（原来漏了），并新增 **`_attach_pool_scores`**：
  一次 `recent_outcomes(cutoff)` 建索引后逐行 `score_signal`，**禁止逐行查库**。
  找不到样本 → `system_available=False`（不伪造 0 分，0 分是「等价于基准」的明确含义）。
- **`system_pick` 补去重**（同 symbol+kind 保留最新），与池子口径一致。
- **新增 `WatchState.SECOND_BUY_OK`（二买守住）**：考验期满且守住 → 归档出圈，
  并在同一次 update 里用「比被归档二买更晚」的一买开新一轮。
  - 加入 `CLOSED_STATES`，**不加入** `COOLDOWN_STATES`（成功不该被冷静期惩罚）。
  - `watchlist_stats` 口径同步：二买成功 = OPPORTUNITY + SECOND_BUY_OK。

### 前端

- 池表/候选表统一列头 `胜算（体系分 / 胜率）`，排序键 `system_score_value`；
  卖点池保持 `rate_value`（无体系分口径）。
- 新增 `systemScoreCell` / `poolRateCell`：体系分居左（主）+ 胜率居右（次），
  体系分 tooltip 列出全部命中特征箱及增益。
- 四个页签 meta 全部写清「统计窗口 / 数据源 / 去重规则 / 过滤条件」，
  关注圈额外说明「状态机口径，数量天然小于买点池，不要直接相减」。

### 关键判断（别改回去）

- **`scan_hits` 是「扫描任务快照」，signals 是「当前信号真相」**。任何要回答
  「现在有哪些买点」的视图都必须读 signals；scan_hits 只服务「扫描历史」页签。

  成功不该被惩罚；它和新一买本来就是不同的下跌结构。
