## 首页查询性能诊断与优化方案（只出方案，未改功能代码）

用户反馈「首页出数据要 20 多秒」，问能否优化 / 换数据库。

### 实测结论（决定性）

- **线上是 nginx 反代 uvicorn**，`Vary: Accept-Encoding` 存在但**无 `Content-Encoding`** → gzip 没生效（`DEPLOY.md:342` 的 server 块里完全没有 gzip 指令）。
- `/api/market/candidates` 线上 **7.00 MB / TTFB 4.81s / 总 63.17s**，下载速度仅 **111 KB/s**。
  → 服务端算完只要 4.8 秒，**58 秒全在传输**。
- `/static/vendor/echarts.min.js` **1.03 MB**，`<head>` 同步加载，线上 **7.83s**（131 KB/s）。
- 本地同代码同库：candidates 冷 6.0s / 热 2.08s、6.43 MB；watchlist 0.10s / 1.05 MB。
- 首页 8 个请求并发时被**同一把 SQLite 锁串行**：`risk` 0.22s→3.98s，`scan/history` 0.005s→5.21s。
- gzip 实测：candidates **6.43 MB → 0.36 MB（18.1×）**；echarts 1.03 MB → 0.33 MB（3.1×）。

### 根因归因

- `candidates` 6s 中 **3.8s 是 `symbol_success_rates(1952 只)`**；内部 `load_close_series` 760ms（78 万行）、`signals_for_symbols` 322ms（18,297 条每条都 `json.loads(meta_json)`，胜率用不到 meta）。
- **395 只纯三买标的被白算胜率**：`_attach_pool_rates` 对所有 grouped symbol 都送进胜率，但 THIRD_BUY 的 `stat_key=None`，`_rate_badge` 直接返回「—」。一买1351+二买277 并集仅 1557 只。
- 胜率被 candidates / pools / risk **各重算一次**；`_exit_medians_by_score` 每次全量 load 25,690 outcomes 再逐条 `score_signal`（451ms），无缓存。
- **真索引缺口**：`signals_for_symbols` 执行计划是 `SEARCH signals USING INDEX idx_signals_period (period=?) | USE TEMP B-TREE FOR ORDER BY` —— `symbol IN` 没走索引，全扫 39,859 条。缺 `(symbol, period, trade_date)` 组合索引。
- 字段体积：`system_hits` 占 **78.2%（5.02MB）**、`meta` 占 11.7%（0.75MB，候选表根本不用）。
- 首屏还预加载了「市场」页签的 `loadSectorHeat` / `loadScanHistory`，而 `switchTab('market')` 已经会调。

### 换数据库判断

**不需要换。** SQLite 544MB / 218 万 bars / 4 万 signals，热查询 0.3–66ms 完全够用。
本次瓶颈是「响应体 7MB × 带宽 110KB/s」，换 MySQL/PG 同样 7MB 同样窄带宽，还要加网络往返。
该换的时机：多实例并发写、>50GB、跨机部署、需要行级锁事务——当前都不满足。

### 产出

- `改造方案-首页查询性能优化.md`：P0（nginx gzip + echarts defer + 首屏去预加载 + health 降频）→ 预计 20s→4-6s；
  P1（只算一买/二买、取数去 meta、加缓存、补索引、候选去 meta）→ 2-3s；P2（服务端分页 / 物化徽章表 / WAL）可选。
- 关键坑记录：nginx 默认 `gzip_types` 只含 `text/html`，**必须显式加 `application/json`**，否则 API JSON 不压缩。

## 折叠扩到全部页签 + 表头吸顶（用户要求「所有页签下的都要这样改」）

### 覆盖面：24 个区块 / 13 张表 / 7 个页签

`frontend/index.html` +239/-50；`tests/test_frontend_contract.py` +133。

只有 2 个 card 没有折叠：市场扫描工具栏、买卖点池口径说明——它们没有 h2，是纯操作/说明区。

### 两个结构型（必须区分，否则收起时按钮消失）

| 型 | h2 位置 | 标记 | 收起规则 |
|---|---|---|---|
| A（20 个） | .card 直接子元素 | 无 | `>` `*:not(h2)` |
| B（4 个：fav/watch/pick/sys） | `.toolbar` 里 | `head-in-toolbar` | `>*:not(.toolbar)` |

**B 型不能用 `:not(.toolbar)` 通吃 A 型**：板块热度卡里也有一个纯内容 toolbar，应该一起收起。

### 实测踩到并修掉的 3 个真 bug

1. **B 型点击无反应**：事件委托里取 `head.parentElement` 判 `collapsible`，但 B 型 h2 的父级是 `.toolbar`。
   → 改 `head.closest('.card.collapsible')`。
2. **B 型 toolbar 被 A 型规则隐藏**：`> *:not(h2)` 也命中 toolbar，而 B 型规则只声明"隐藏非 toolbar"、并不会把 toolbar 恢复。
   → A 型规则加 `:not(.head-in-toolbar)` 排除。
3. **空状态提示残留**：`.empty` 的 `display:block` 是 JS 写的 **inline style**，普通选择器盖不住，
   折叠后「暂无数据」浮在标题下。→ 收起规则加 `display: none !important`（只在 `.collapsed` 命中，展开不受影响）。

### 表头吸顶要点

- `table thead th { position: sticky; top: var(--sticky-top, 110px); z-index: 4; background: var(--panel) }`
- `--sticky-top` = headerH + navH（实测 60 + 55 = 115px），由 `syncStickyOffset()` 一并写入。
- **z-index 必须 < nav(9)**，表头滑到页签位置时藏在页签下面。
- **`border-collapse: collapse` 下 sticky th 的 border 会随滚动丢失** → 底线改用 `box-shadow: inset 0 -1px 0`。
- **移动端 860px 以下必须关掉**：`table { display:block; overflow-x:auto }` 让 table 自己成了滚动容器，th sticky 会相对它计算而错位。`@media` 里 `table thead th { position: static }`。

### 图表区块额外处理

`refreshChartsIn(card)`：展开时 `requestAnimationFrame` 里先派发 `window resize`（走已有监听），
再对 `#chart, #tf-grid *` 里所有 `echarts.getInstanceByDom` 实例 `resize()`。
实测 K 线图折叠再展开仍为 1318×520，canvas 同尺寸，未塌陷。

### CDP 实测结果

24 区块全部可收起；B 型 toolbar/按钮/标题全保留、正文全隐藏；
表头滚动 1015px 后 thTop=115 与 `--sticky-top` 一致；watch/pools/pick/system 表头均 sticky 115px；零控制台错误。
全套 **478 项通过（8 skip）**。

### 一处被实测否掉的设计

最初给 B 型 h2 加 `flex:1` 想把 caret 推到最右，结果 caret 被夹在标题和「重评关注圈」按钮**之间**。
已删掉——B 型保持 h2 内容宽度，caret 紧贴标题（实测 caret 143px < 按钮 162px），点击指向更明确。

## 替代数据源实测：东财 HTTP + baostock（都比通达信靠谱）

用户问「还有没有其它方式拿数据」。实测三个候选，结论：

| 源 | 日线深度 | m30 深度 | 盘中实时 | 分钟复权 | 限流 |
|---|---|---|---|---|---|
| westock（现状） | 400 根 | **10 天** | ✅ | ❌ 强制不复权 | 有 |
| 通达信 pytdx/mootdx | ❌ 拿不到 | ❌ | ❌ | — | — |
| **东财 HTTP** | **6024 根 / 25 年** | 251 根 ≈ **31 天** | ✅ **当天正在形成的 K 线** | ❌ `fqt` 对分钟无效 | 连续 8 只后 RemoteDisconnected |
| **baostock** | 2863 根 / 11 年 | **13152 根 / 6.8 年（2020-01 起）** | ❌ T+1 | ✅ **三种复权都支持** | 未触发 |

### 东财 HTTP 要点

- 接口 `https://push2his.eastmoney.com/api/qt/stock/kline/get`
  参数 `secid`（1.=沪 0.=深）、`klt`（1/5/15/30/60/101日）、`fqt`（0不复权 1前复权 2后复权）、`beg/end/lmt`
- **必须带 UA + Referer**，否则被拒。
- **复权真实生效**（实测）：茅台 2026-06-15 不复权 close=1271.10、前复权 close=1243.08，
  差 **28.02 元** = 每股分红（xdxr `fenhong=280.24`/10股）→ 完全对得上。
- **分钟线 `fqt` 无效**：fqt=0 与 fqt=1 的 m30 完全一致。
- **分钟只有约 31 个交易日**：传 `beg=2025xxxx` / `beg=2024xxxx` 都只返回 251 根、起点固定 2026-08-28，
  是服务器端硬限制，翻页/改起始日期都取不到更早。
- 盘中有用：10:36 请求能拿到 `2026-10-20 11:00` 那根正在形成的 K 线。

### baostock 要点（本次最大发现）

- `pip install baostock`，`bs.login()` 免密。`adjustflag`: 1后复权 2前复权 3不复权。
- **m30 = 13152 根 / 2020-01-02 ~ 至今，约 1638 个交易日** —— 是现状（10 天）的 **160 倍**，
  足够做 p100「大级别二买由次级别一买构成」的验证。
- m15 = 26304 根，同样 2020 起。
- **分钟线复权真实生效**：除权日附近 m30 三个值全不同（不复权 1222.30 / 前复权 1194.04 / 后复权 9157.43）。
  → 这一点比 westock（分钟强制不复权）和东财（fqt 无效）都强。
- 日线 2863 根（2015 起，前复权）。查询日线时 **fields 不能带 `time`**，否则报
  `日线指标参数传入错误:time`。
- **T+1**：末条是 2026-10-19 15:00，当天数据要收盘后才有 → 正好匹配「收盘后全量重算」。

### 推荐组合

1. **baostock → 历史主源**（深度 + 复权，T+1，收盘后跑）
2. **东财 HTTP → 盘中实时**（当天最新 K 线，轻量，需节流）
3. **westock → 兜底/交叉校验**

### 必须提醒的口径变化

换成 1638 天 m30 后，**历史分钟信号会整体改变**（中枢/趋势/背驰在更长窗口下判定不同），
`bar_index`/`anchor_index` 也会变。必须重扫并接受"历史 m30 信号全部重算"。
signals 表身份键已不含 bar_index（`SIGNAL_IDENTITY_COLUMNS`），不会产生重复，但结论会变。

## 多源互补落地（用户要求「全做了，以互补形式同步进行」）

### 新增模块

```
backend/sources/
├── __init__.py            # 对外只暴露 registry
├── base.py                # 符号转换 / merge_bars 合并校验 / OHLC 归一
├── eastmoney.py           # 东财 HTTP：日线25年 + 分钟31天 + 实时报价
├── baostock_source.py     # baostock：m30 13152根/6.8年、分钟复权
└── registry.py            # 互补调度 + 降级 + 熔断状态
scripts/sync_history.py    # 补历史（默认约1年，--days 0 全量）
tests/test_multi_source.py # 23 条纯离线用例
```

### 核心设计决策（都是实测逼出来的）

1. **对外签名不变**：`provider.fetch_bars` 内部换成多源，`service.py` 与大量
   `mock.patch.object(service_module, "fetch_bars")` 的打桩全部不受影响。
2. **日线绝不跨源合并**：实测东财与 baostock 的前复权基准不同——400 根里 **71 根偏差 >0.5%、最大 0.99%**。
   混用会在除权处留断层，笔/中枢判定会静默翻转。日线只取单一源（优先东财，失败整段换 baostock）。
3. **分钟可以合并**：两边都不复权，实测重叠 248 根、**冲突 0、最大偏差 0.0077%**。
4. **分钟强制不复权**（`effective_fq`）：与已落库的历史 signals 保持可比。
5. **日线盘中不补当天**：东财盘中会返回未收盘日线，用它算中枢收盘后可能全不成立。剔除。
6. **`needs_tail` 用数据判断不用时钟**：baostock 末条已覆盖今天就不打东财，省配额省时间。
7. **东财熔断**：连续失败后冷却 60s。不熔断的话，超时+重试会把详情页拖到十几秒。
8. **测试进程默认关闭多源**（`"unittest" in sys.modules`）：否则漏一处 mock 就会真的联网，
   套件变慢变脆。显式设置 `CHANPICKER_SOURCE` 时以显式值为准。

**踩过的坑**：
- baostock 若固定从 2020 拉全量再裁剪，取 500 根 m30 要 **26 秒**；按 `days` 反推起始日后 **2 秒**（快 12 倍）。
- 东财 `lmt` 参数会被忽略（要 10 根返回 2492 根），必须自己截断，否则整段重叠把复权差异全算成冲突。
- 东财报价必须请求 `f13`（市场号），否则深市票被标成 `sh`。
- 东财超时原本 15s×3 次重试，失败时一次请求要拖 45s+ → 压到 5s×2 次 + 熔断。
