**全市场扫描**：5028/5028 完成，16257 个信号，命中 8974 条。全量重评后：一买成功率 **12.9%**(512/3983)、二买成功率 **83.4%**(427/512，85 只二买失败)、在圈 1984 / 已出圈 2455。

**库现状**：SQLite 449 MB；bars 2,184,674 行 / signals 38,562 / symbols 5,028 / watchlist 4,439 / scan_hits 17,558。

### 关键发现：慢查询根因是缺索引，不是数据库选型

实测（热缓存）：
- `recent_trading_dates(3)` = **8990 ms** ← `SELECT DISTINCT trade_date ... WHERE period=?` 全扫 218 万行，现有索引是 `(symbol, period, trade_date)`，period 不是前导列用不上
- `period_counts()` = **7809 ms** ← `GROUP BY period` 同样全扫
- 其余 10 个查询**全部 ≤ 40 ms**；`load_bars` 单股 400 根仅 **0.7 ms**

加 `bars(period, trade_date)` 索引后（建索引仅 5.5 s）：
- `recent_trading_dates` 3760 → **0.2 ms**（18000×）
- `period_counts` 3802 → **55 ms**

### 部署条件变更（影响选型结论）

用户改口：**数据库与应用同机，走 127.0.0.1，机器 4c4g**。远程 MySQL 115.190.254.139 实测：5.7.44-log / utf8mb4 / buffer_pool 256MB / max_allowed_packet 1024MB / innodb_large_prefix=ON / 只有 `stock.*` 权限（不能建库）。

### 选型结论：ClickHouse 是错的选型

理由（基于实测数据，不是通用套话）：
1. **业务是 OLTP 点查不是 OLAP 扫描**：218 万行里单次只取 400 行（0.018%），无跨股聚合报表
2. **高频单条 upsert 是 CH 硬伤**：`symbols` 5028 次、`watchlist` 5028 次、`scan_runs` 251 次逐条写；CH 的 UPDATE 是异步 mutation，ReplacingMergeTree + FINAL 会让每次查询付代价
3. **数据量不够**：220 MB 在 ClickHouse 的价值区间（亿级）之下三个数量级
4. **4 GB 内存撑不住**：CH 官方建议 ≥8 GB，4c4g 上 CH 会和应用抢内存导致 OOM
5. **`symbol_name()` 点查**：CH 需扫 granule（8192 行/块）取 1 行，5-50 ms；MySQL/SQLite <0.1 ms

推荐：**MySQL 5.7 同机 localhost**（RTT≈0.05ms，网络开销归零），加索引 + 批量化。若确定单实例单用户，SQLite 加索引也是够的（零运维）。

## 信号去重 + 个股级成功率（用户需求：成功率要按个股自身统计）

### 摸底发现的真问题

1. **`signals` 表有 36% 重复**（42624 行里 15416 行是同一个信号被插两遍）。根因：`UNIQUE(symbol,kind,anchor_index,period)` 用 `anchor_index` 做键，但它是 K 线窗口内的相对位置——用户传 `days=600` 时同一个底分型下标就变了，同一信号被当成新的再插一条。直接影响：个股级历史次数会**翻一倍**。
2. **`watchlist` 表按 symbol 唯一**，表达不了「历史上第 1 次一买成功、第 2 次失败」，个股级成功率必须从 signals 表按时间线重建。
3. **样本普遍偏小**：去重后一买涉及 4439 只，仅 **1559 只（35.1%）样本 ≥3 次**；1 次的占 30.6%。

### 实施

- `Store.SIGNAL_IDENTITY_COLUMNS = (symbol, kind, period, trade_date, price, anchor_price)`；`_migrate_signal_identity()` 幂等去重 + 重建表；`save_signals` 冲突键同步换掉（并保持 meta 刷新，否则背驰段坐标补不上）
- 实测去重：42624 → 27208 行（-36%）。买点池条目数不变（4439，本来就按 symbol+kind 去重）；全市场成功率不变（来自 watchlist 表）
- `ScanService.symbol_success_rate(symbol)`：一买成功 = 之后 30 个**交易日**内出二买；二买成功 = 窗口内未跌破低点（查真实 K 线）；样本 <3 只给明细
- `GET /api/market/success-rate?symbol=xxx`（省略 symbol 返回全市场）；个股分析接口带 `symbol_success_rate` 字段；前端个股页结论区加成功率面板

### 踩过的坑

1. `_migrate_signal_identity` 里先 DELETE 再 `_run_script`（内部会 BEGIN）→ **事务嵌套报错**。sqlite3 不允许事务内再 BEGIN，要自己管理 BEGIN/COMMIT/ROLLBACK。

## 复盘：当前代码的一二买点 vs 缠论原文（术与道的差距）

逐条回原文核对（/tmp/chan108.txt），发现**四项结构性差距**，都出在「道」这一层。

### 原文对一买的定性（p98-99）

> 「第一类买点：用比较形象的语言描述就是由**男上位最后一吻后出现的背驰式下跌**构成。」
> 「第一吻后的下跌一般不会构成买点，**必须是至少第二吻以后**。」（p98）

四个必要条件：
1. **男上位**（短期均线在长期均线之下）
2. 是**最后一吻之后**的下跌
3. 该下跌构成**背驰**（绿柱缩短 + 创新低）
4. 位置在大级别中枢之下

p98 星注另给一例：一吻后下跌若把前面部分走势组合起来形成同级别箱体，「也可以形成趋势一买」——说明"一吻"不是硬排除，而是有条件。

### 原文对一买/二买关系的定性（p100）

> 「这里给出一个**缠中说禅买点定律**：大级别的第二类买点由**次一级别相应走势的第一类买点**构成……有了这个定律，**所有的买点都可以归结到第一类买点**。」

### 代码现状（`_detect_first_buy_by_legs` / `_detect_second_buy_by_legs`）

已实现：
- ✓ 背驰三条件（p368）+ 标准背驰 + 趋势背驰（p116）
- ✓ 低点在中枢 ZD 之下
- ✓ 二买「第一次次级别回调」「不破一买低点」（p152-153）

缺失（**都是「道」层，不是「术」层**）：
- ✗ **「男上位」判定**：代码里根本没有均线相对位置的概念，只有 MACD 与一根均线偏离度（且那根还只是交叉验证项）
- ✗ **「吻」的概念**：原文的一买依赖"第几吻"，代码完全没有吻的计数
- ✗ **一买/二买的级别递归关系**（p100 买点定律）：代码把两者当成同一层级的两个独立判定，而原文是"大级别二买 = 次级别一买"的递归

### 结论

**术**（背驰怎么算、中枢怎么划）我们已基本对齐原文；**道**（买点为什么成立、彼此什么关系）差三层：
均线位置体系（男上位/女上位）、吻的计数、级别递归。补齐这三项不是加几个条件，而是要把整个"结构判定"从"段+中枢"扩展到"均线位置+吻+多级别递归"。

短期建议：若不动这三项，**必须明确标注「一二买点为本系统自定义口径，非缠论严格定义」**，否则用户会误以为是缠论买点。

## 批次9：30分钟区间套（用户选「30分钟区间套」块，已下令「开始编码」）

### 设计
区间套 = 用 30 分钟（次级别）同位置结构确认日线（大级别）买点，是 p100 买点定律（大级别二买由次级别一买构成）的泛化。与既有 `sublevel_second_buy_confirmations`（只查二买后 5 日内有无 m30 一买）不同，区间套对任意日线买点定位同位置 m30 买点，并给出精确入场时间/价。

**数据现实（必须尊重）**：westock 的 m30 仅保留约 9-10 个交易日 → 只有落在最近窗口内的日线买点才做得了区间套；早于窗口的日线信号 m30 早已无留存。故设计成**按需按钮**触发（不在每次日线分析自动跑，避免网络惊吓与限流），与既有 sublevel 确认一致。窗口外的日线买点 `available=True` 但 `confirmed=False` 并如实说明，**绝不**用无关远端信号假确认。

### 实施
- `backend/service.py`：`interval_nesting(symbol, anchor_date, anchor_kind, m30_bars)`——解析日线买点 anchor（省略则从本地日线信号取最近买点）→ 取 m30 K 线（本地缓存优先，不足则远端拉取并落本地）→ 检查窗口覆盖 → `ChanEngine.scan(m30)` 找同位置（anchor 日 ±3 天，同日优先一买）m30 买点 → 返回结构化确认；辅助 `_m30_structure()` / `_interval_nesting_message()`；常量 `INTERVAL_NESTING_WINDOW_DAYS=3`
- `backend/app.py`：`GET /api/market/interval-nesting?symbol=&date=&kind=`
- `frontend/index.html`：API 加 `intervalNesting`；分析面板加「30分钟区间套」按钮（`btn-nesting`）+ `#nesting-box` 容器 + `renderIntervalNesting()`（确认/未确认/窗口外三态）+ `KIND_LABELS_SHORT`；新分析时重置 nesting-box
- 新增 `tests/test_interval_nesting.py`(6) + `tests/test_frontend_contract.py::IntervalNestingContractTest`(4)

### 验证
全量回归 **293 例全绿**（skipped=8）；app 路由 `/api/market/interval-nesting` 已注册；`py_compile` 通过。
