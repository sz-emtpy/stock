# 四个视图买点数量对不上 — 排查与修复报告

**日期**：2026-10-17
**问题**：市场扫描 / 关注圈 / 三日买卖点池 / 体系选股 中「同一买点数」对不上
**环境**：本地 + 服务器 `http://stock.temeu.top`（2026-10-17 22:57 刚完成全市场扫描）

---

## 一、排查结论：不是单一 bug，是 3 个缺陷 + 1 个设计差异

### 实测差异（服务器真实数据）

| 视图 | 一买 | 二买 | 三买 | 窗口 | 数据源 |
|---|---|---|---|---|---|
| 市场扫描 | 145 | 4 | 242 | 30 **自然日** | `scan_hits` 快照 |
| 三日买卖点池 | 470 | 38 | 83 | 3 **交易日** | `signals` 表 |
| 关注圈 | 88（近 3 日） | 29 | — | 状态机全历史 | `watchlist` 表 |
| 体系选股 | 387 | 37 | 76 | 3 交易日 + 分数过滤 | `signal_outcomes` |

同一 20 交易日窗口下的对比更刺眼：**`signals` 表一买 1404 条，`scan_hits` 只有 145 条，差近 10 倍**。

### 缺陷 1：`scan_hits` 主键缺 `trade_date`（数量差 10 倍的直接原因）

主键是 `(run_id, symbol, kind)`。一次扫描里，同一只股票 400 根 K 线会产出**多个**同类买点
（比如 2025-11 和 2026-03 各一个一买），`ON CONFLICT DO UPDATE` 让后者覆盖前者 →
整张表只剩「每股票每类最新一条」。

### 缺陷 2：市场扫描读 `scan_hits` 快照，三日池读 `signals` 表（同一买点忽隐忽现）

- `analyze` 个股详情会把新信号写进 `signals`，但**永不写** `scan_hits`
- `_prune_stale_signals` 清理过时信号时只清 `signals`，`scan_hits` 是冻结快照不受影响
- 结果：市场扫描里有、点进详情找不到；或反过来

### 缺陷 3：关注圈僵尸记录（数量永远对不上的深层原因）

二买确认后，超过 `max_wait_bars`（30 根）时原代码直接 `return items`，状态**永久停在
`OPPORTUNITY`**，既不算成功也不算失败，占着 active 位。

- 实测服务器 **49 条超过 365 天**的僵尸记录，最老 **591 天前**
- 后果：这些股票后来出现新一买时，`active` 已存在 → 无法开启新一轮跟踪
- 例：`sz002370` 在 2026-10-15 出了新一买，关注圈里 `first_buy_date` 仍是 **2025-03-12**

### 缺陷 4（顺带发现的功能缺失）：买点池的胜算列一直是空的

`_attach_pool_rates` 只在 `risk_pool`（卖点池）里被调用，**`pools()` 从来没调用过**。
这就是为什么「胜算」列此前一直显示「—」。

### 设计差异（不是 bug，需要说明而非修复）

关注圈是**状态机跟踪池**，与「买点清单」本质不同：

- 一买失败（`FAILED`）、二买失败（`SECOND_BUY_FAILED`）会**出圈**
- 一只股票只保留**当前一轮**记录

所以关注圈数量天然小于买点池，**不该直接相减**。这一点已写进界面提示。

## 二、修复内容

### 后端

| 文件 | 改动 |
|---|---|
| `backend/service.py` | `candidates()` 改读 `signals` 表（与 `pools` 同源），窗口改交易日语义，复用 `_group_recent` 去重，返回 `trading_dates`/`source`/`dedup` |
| | `pools()` 补上遗漏的 `_attach_pool_rates`，并新增 `_attach_pool_scores`（挂体系分） |
| | `system_pick()` 补去重（同 symbol+kind 保留最新），与池子口径一致 |
| | `watchlist_stats()` 口径更新：二买成功 = `OPPORTUNITY` + `SECOND_BUY_OK` |
| `backend/store.py` | `scan_hits` 主键加 `trade_date`；新增幂等迁移 `_migrate_scan_hits_identity` |
| `backend/app.py` | `/api/market/candidates` 支持 `period` 参数 |
| `src/chanpicker/core.py` | 新增 `WatchState.SECOND_BUY_OK`（二买守住）；状态机在考验期满守住的场景归档并开新一轮 |

### 前端

- 池表 / 候选表列头统一为 `胜算（体系分 / 胜率）`，排序键 `system_score_value`
- 新增 `systemScoreCell` / `poolRateCell`：体系分居左（主）+ 胜率居右（次），体系分 tooltip 列出全部命中特征箱
- 四个页签 meta 全部写清「统计窗口 / 数据源 / 去重规则 / 过滤条件」
- 关注圈明确标注「状态机口径，数量天然小于买点池，不要直接相减」

## 五、口径速查（记住这张表就不会再困惑）

| 视图 | 数据源 | 窗口 | 去重 | 过滤 | 与其他视图的关系 |
|---|---|---|---|---|---|
| 市场扫描 | `signals` | 30 交易日（可调） | 同股票同类型留最新 | 无 | 与三日池同源，只差窗口 |
| 三日买卖点池 | `signals` | 3 交易日 | 同上 | 无 | 市场扫描传 `recent_days=3` 时**完全相等** |
| 体系选股 | `signal_outcomes` | 3 交易日 | 同上 | 体系分 ≥ `min_score` | **三日池的子集** |
| 关注圈 | `watchlist` | 全历史 | 一只股票一条 | 只返回跟踪中状态 | 独立口径，**不要相减** |

## 六、关键设计决策（别改回去）

1. **`scan_hits` 是「扫描任务快照」，`signals` 是「当前信号真相」**
   任何回答「现在有哪些买点」的视图都必须读 `signals`；`scan_hits` 只服务「扫描历史」页签。

2. **`candidates` 与 `pools` 必须共用同一取数函数**
   自己写一套 SQL 就会重新漂移。`test_view_consistency` 锁死了「数量相等 + 集合相等」。

3. **体系分缺失时给 `None`，不给 0**
   0 分在体系里有明确含义（命中特征增益恰好抵消），和「没算过」不能混为一谈。

4. **`SECOND_BUY_OK` 是成功终态，不进 `COOLDOWN_STATES`**
   冷静期是为了防「刚失败又重新入圈」，成功不该被惩罚。
